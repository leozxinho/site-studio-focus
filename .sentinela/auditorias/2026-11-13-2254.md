## 4. Melhorias de arquitetura para decisão do usuário

### A. Papel de admin explícito na RLS
- Problema atual: as policies `admin_all ... to authenticated using (true)` aparecem em 16 tabelas (nas duas migrations). Ser admin equivale a estar autenticado, e a segurança depende de duas configurações no painel do Supabase.
- Proposta:
  ```sql
  create function public.is_admin() returns boolean language sql stable
  set search_path = '' as $$
    select coalesce((auth.jwt()->'app_metadata'->>'role') = 'admin', false) $$;
  -- em cada tabela:
  create policy admin_all on public.alunos for all to authenticated
    using (public.is_admin()) with check (public.is_admin());
  ```
  Para definir o papel: `update auth.users set raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}' where email = '…'`.
- Benefício: um signup acidental, um login anônimo ou uma conta criada por engano deixa de ter acesso a qualquer dado.
- Custo e risco: uma nova migration e a definição da claim no usuário admin atual. Se a claim for esquecida, o admin perde acesso até corrigir.
- Esforço: baixo. Dá para fazer de forma incremental, tabela por tabela.

### B. Backend único de alarmes
- Problema atual: a landing grava no Worker com KV (`index.html:3298`). O portal grava em `alarmes_push` no Supabase (`treinos/index.html:2457`), que é lido por um script do GitHub Actions ausente do projeto (`scripts/check-alarms.js`). Há dois crons, duas deduplicações e os problemas dos achados 5, 8 e 11.
- Proposta: um só Worker `studio-focus-alarms` para os dois clientes, com `POST /subscribe` validado e KV indexado por minuto:
  ```
  player:<id>       -> {alarms}           (fonte da verdade)
  due:HH:MM         -> [{id, title, body, tag}]   (índice; 1 get por minuto)
  ```
  O portal passa a chamar o Worker. A tabela `alarmes_push`, a RPC `alarmes_sync` e o `check-alarms.js` são removidos.
- Benefício: um único caminho de disparo, custo fixo por minuto e um só ponto para validação e rate limit.
- Custo e risco: migrar os registros existentes de `alarmes_push`, que exige leitura com service role e é feita pelo usuário, e mudar o front do portal.
- Esforço: médio. É incremental: primeiro o portal passa a gravar nos dois lugares, depois o legado é desligado.

**Minha recomendação:** fazer a A primeiro. É barata, fecha o único caminho para acesso total aos dados e combina com a aplicação das migrations que você ainda vai fazer. A B pode vir depois de resolver os HIGH, porque o impacto dela é funcional e de custo, não de vazamento.
